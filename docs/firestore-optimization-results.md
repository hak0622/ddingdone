# 사진 저장과 Firestore 호출 비교

기준 커밋은 `9df1f1709`다. 수정 전후를 같은 머신의 헤드리스 Chromium에서 번갈아 실행하고, 같은 Firebase Auth·Firestore 에뮬레이터(`demo-ddingdone`)에 연결했다. 운영 서버와 운영 데이터는 측정에 쓰지 않았다.

## 사진 저장

원본 종류마다 버전별로 워밍업 3회와 대표 사진 교체 20회를 실행했다. 시간 단위는 ms다. 저장 확인은 버튼 클릭부터 SDK의 서버 응답까지, 사진 표시는 같은 클릭부터 새 이미지의 로드 이벤트까지다. p95는 20개 표본을 정렬한 뒤 19번째 값이다.

| 원본 | 저장 확인 중앙값 | 저장 확인 p95 | 사진 표시 중앙값 | 사진 표시 p95 |
| --- | ---: | ---: | ---: | ---: |
| 일반 | 118.8 → 115.0 | 126.0 → 128.1 | 137.5 → 133.3 | 145.0 → 147.2 |
| 고디테일 | 243.3 → 238.2 | 276.2 → 263.0 | 262.1 → 255.8 | 300.3 → 281.1 |
| EXIF 회전 | 120.3 → 118.0 | 129.2 → 126.5 | 139.8 → 136.7 | 149.6 → 147.4 |

| 원본 | 압축 중앙값 | 서버 저장 구간 중앙값 | 양쪽 JPEG 결과 | 인코딩 시도 |
| --- | ---: | ---: | --- | ---: |
| 일반 4,000×3,000 | 86.9 → 84.6 | 31.4 → 28.5 | 201,374 B, 1,200×900 | 1 |

| EXIF 90° 회전 | 89.4 → 89.2 | 31.1 → 28.9 | 201,190 B, 900×1,200 | 1 |

두 버전 모두 측정 60회에서 실패 0건이었다. 배치 후보는 앱의 저장 전 모임 문서 조회를 매번 1회에서 0회로 줄였다. 사진 저장은 두 문서를 한 번에 썼고, 새 버전의 사진을 표시하는 서버 조회는 매번 1회로 유지됐다. 규칙은 양쪽에서 동일하게 모임·사진 버전과 탈퇴 잠금 문서를 확인했다. 에뮬레이터 호출 수와 규칙 참조 수는 운영의 과금량과 별도로 다룬다.

초기 저장, 동시 교체, 오프라인 중 저장 실패와 재연결, 권한 상실, 확정·삭제된 방, 탈퇴 잠금, 커밋 성공 후 응답 유실을 검증했다. Cloudinary 시절의 4.73초와 1.52초는 과거 기록이다. 당시 네트워크와 타이밍 원본이 확인되지 않아 로컬 결과와 묶어 단축률을 산출하지 않았다.

## 화면과 Worker 작업 수

로컬 Worker와 3인 모임의 지출 100건을 사용했다. 표는 실제 화면이 보낸 Firestore 구독·조회·커밋 요청과 Worker HTTP 호출을 비교한다. 지출 결과 건수는 해당 구독이 열린 시나리오에서 준비한 문서 수다. 초대 비멤버의 기존 지출 구독은 규칙에서 거절됐다.

| 시나리오 | 전체 지출 구독 | 전체 지출 결과 | 단건 지출 대상 | Worker 호출 |
| --- | ---: | ---: | ---: | ---: |
| 모임 기본 정보 수정 직접 진입 | 1 → 0 | 100 → 0 | 0 → 0 | 1 → 1 |
| 새 비용 입력 직접 진입 | 1 → 0 | 100 → 0 | 0 → 0 | 1 → 1 |
| 기존 비용 수정 직접 진입 | 1 → 0 | 100 → 0 | 0 → 1 | 1 → 1 |
| 완료 정산 직접 진입 | 1 → 0 | 100 → 0 | 0 → 0 | 1 → 1 |
| 미가입자의 초대 링크 | 1 → 0 | 0 → 0 | 0 → 0 | 1 → 1 |
| 상세 → 새 비용 → 상세 | 1 → 1 | 100 → 100 | 0 → 0 | 1 → 1 |

홈의 내 모임 쿼리는 1회로 유지됐다. 설정에서 닉네임을 변경하면 내 모임 조회 요청과 구형 경로 쓰기 요청이 각각 1회에서 0회로 줄었다. 기존 쓰기는 규칙에서 거절됐다. 동일 금액의 분담 수정은 Worker 테스트에서 기존 지출·모임 문서 쓰기 2건에서 지출 문서 쓰기 1건으로 줄었다. 분담 수정과 정산 확정이 겹치는 경우에도 확정 해시가 실제 장부와 일치했다. 비교 동선에서 문서 삭제 건수는 0이었다.

탈퇴 상태 응답을 고정한 브라우저 시뮬레이션에서는 30초 동안 상태 요청이 **31회 → 6회**로 줄었다. 같은 시뮬레이션에서 약 30초 시점에 완료 응답을 활성화했을 때 다음 조회까지 969ms → 977ms가 걸렸다. 조회 간격이 최대 8초까지 늘어나므로 완료 시점에 따라 표시 지연도 달라진다. 화면이 숨겨지면 예약 조회가 멈추고, 복귀와 재확인 후에는 즉시 확인하며, 완료 응답 뒤에는 조회를 종료했다.

## 모임 정보 수정과 월·페이지 조회

모임 정보 수정에 직접 진입하면 모임 문서와 Worker 접근 확인을 사용하고, 참여자·지출 컬렉션 구독은 각각 0회다. 같은 방에서 분담 대상을 사용하는 화면으로 이동하면 참여자 구독을 한 번 열고 기존 접근 확인 결과를 재사용한다. 이 동작은 훅 테스트에서 확인했다.

Firestore 에뮬레이터에서 기존 전체 목록과 새 조회가 반환한 문서를 비교했다.

| 준비한 모임 수 | 기존 전체 목록 | 홈 선택 월 | 내역 첫 페이지 | 새 두 범위의 최초 반환 문서 합계 |
| ---: | ---: | ---: | ---: | ---: |
| 5 | 5 | 1 | 5 | 6 |
| 100 | 100 | 10 | 21 | 31 |

내역은 20개를 표시하고 다음 페이지 여부를 확인하기 위해 최대 21개를 읽는다. 탭을 30초 안에 세 번 왕복할 때 구독이 범위별로 한 번씩만 등록되는 것은 모의 리스너로 별도 검증했다. 위 표는 두 최초 결과의 합계이며, 운영 과금이나 화면을 떠난 동안의 변경량을 측정한 결과는 아니다.
