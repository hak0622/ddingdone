# 대표 사진 이전 운영 순서

## 앱인토스 1회 출시로 마무리

최종 앱은 v2 모임과 Firestore 대표 사진을 사용한다. 구형·v1 모임의 운영 전환과 사진 표시 검증을 먼저 마치고, 최종 번들을 한 번 검토받아 출시한다. 아래 절차는 완료된 운영 전환의 기록이다.

1. 현재 일반 토스 앱이 전환된 v2 모임과 Firestore 사진을 조회하고 비용 등록·분담·정산도 처리하는지 전용 테스트 방으로 확인한다. 현재 출시본이 이 기준을 충족하지 않으면 무중단 전환을 멈춘다. 최종 번들을 먼저 출시하면 남은 구형·v1 방을 열 수 없다.
2. 출시 전에 운영 사전 검사를 다시 실행하고 전환 가능한 방을 소량씩 옮긴다. 금액이나 송금 관계가 바뀌는 방은 관련 계정이 모두 테스트용으로 확인된 경우에만 예외를 적용한다. 구형 방이 새로 생성되지 않는지와 v2 전환 대상이 0개인지 출시 직전에 다시 확인한다. 최종 앱의 사진 저장은 `photoVersion`과 사진 문서만 갱신한다. Cloudinary 참조가 남은 v2 방에서도 이 쓰기를 허용하는 규칙을 최종 번들보다 먼저 적용하고 확인한다.
3. 이전 사진이 Firestore에서 표시되는지 최종 번들의 iOS·Android QR과 실제 일반 토스 앱에서 확인한다. 복구할 수 없는 404 사진은 기존 대로 이번 검증과 원본 삭제에서 제외한다. 확인된 최종 `.ait`를 단 한 번 출시한다.
4. 출시 뒤 구버전의 사진 경로를 차단하고 기존 도구로 확인된 원본을 한 장부터 삭제 예약한다. 참조와 대기열이 정리된 뒤 사진 전용 Worker, 계정 Worker의 Cloudinary 호출, 관련 비밀값과 구형 백엔드 규칙·색인을 정리한다. 데이터와 Worker·규칙·색인만 바뀌는 작업에는 새 앱 번들이 필요 없다. 미확인 참조나 구형 탈퇴 작업이 남으면 관련 백엔드 코드는 보류한다.

## 당시 호환 버전 확인

1. 앱인토스에서 SDK 3.10.0 전환 전용 버전을 출시하고 기존 정산방을 다시 열어 확인한다.
2. Firestore 운영 프로젝트의 기존 인덱스 설정을 대조한다. 배포할 인덱스에서 `photos.bytes`만 면제한다. CLI가 기존 운영 인덱스 삭제를 제안하면 취소하고 기존 정의를 병합한다.
3. Firestore 규칙과 인덱스, 계정 탈퇴 Worker를 배포한다. 이전 코드로 실행 중인 탈퇴 Workflow가 끝난 뒤 사진 버전의 QR을 iOS와 Android에서 확인한다. 새 테스트 방, 기존 사진이 있는 방, 별도 탈퇴 테스트 계정을 사용한다. 정산방 열기, 저장·교체, 방 삭제, 탈퇴를 확인한다.
4. 앱인토스에서 사진 버전의 동일 번들을 검토 요청하고 승인 후 출시한다. 복사를 시작할 방에서 구형 앱의 사진 변경에 의존하는 사용자가 있는지 확인한다. Firestore 사진 버전이 생기면 해당 방에서 구형 Cloudinary 필드 변경은 제한된다.

## 마이그레이션

macOS의 `sips`와 운영 Firestore 읽기·쓰기 권한이 있는 OAuth 액세스 토큰을 사용한다. 토큰은 `FIRESTORE_ACCESS_TOKEN` 환경 변수로만 전달한다. 기본 실행은 쓰기 없는 목록 조사다.

```sh
node scripts/migrate-cover-photos.mjs --project PROJECT_ID --cloud CLOUD_NAME
node scripts/migrate-cover-photos.mjs --project PROJECT_ID --cloud CLOUD_NAME --copy --limit 5 --budget USAGE.json
```

`USAGE.json`에는 기존 전체 저장량과 예상 용량 `storageBytes`, 이번 달 사용량과 예상 다운로드 `outboundBytes`, 당일 사용량과 예상 사용량 `reads`, `writes`, `deletes`를 숫자로 넣는다. 사진 조회 규칙이 참조하는 모임 문서 읽기도 예상량에 포함한다. 각 묶음 직전에 최신 사용량을 반영한다. 도구는 묶음의 추가 사용량을 더해 무료 한도 80%에 닿으면 쓰기 전에 중단한다.

첫 묶음은 최대 5장이다. 복사를 마친 모임의 홈과 상세에서 표시되는지 확인한 뒤 최대 50장씩 반복한다. 복사는 Firestore 사진과 버전을 함께 저장하고 사본을 다시 읽어 검증한다. Cloudinary 참조와 삭제 대기열은 그대로 유지된다. 출력에서 각 사진의 `receipt`가 포함된 JSON 한 줄을 파일로 보관한다. 실패하면 묶음을 중단하고 해당 방을 확인한 뒤 재실행한다. 검증된 방 다음으로 진행할 때는 `--after MEETING_ID`를 사용한다.

원본 URL이 열리지 않는 모임을 보류하고 확인된 모임만 복사할 때는 `--copy --meeting MEETING_ID --budget USAGE.json`으로 모임을 지정한다.

## 이전 결과와 장애 대응

운영에서는 Firestore 사본 7장의 버전과 해시를 대조한 뒤 Cloudinary 원본을 정리했다. 구형 비서명 업로드를 차단했고, Cloudinary 참조와 삭제 대기열이 0건인 것을 확인한 뒤 사진 전용 Worker와 계정 Worker의 삭제 대기열 처리를 제거했다.

대표 사진 표시 문제는 Firestore의 모임 사진 버전, `photos/cover` 문서와 멤버십을 대조해 확인한다. 과거 사진의 목록 조회와 복사에 사용한 도구는 참고용으로 보관한다.
