# 트러블슈팅

## TS-001: Firestore 무료 플랜 읽기 할당량 — 화면 전환 시 중복 구독으로 인한 읽기 낭비

### 배경

띵돈은 백엔드 서버 없이 Firebase(Firestore)만으로 동작하는 구조다(ADR-002).
무료 Spark 플랜에는 Firestore 읽기 50,000회/일, 쓰기·삭제 20,000회/일이라는
일일 할당량이 있고, 이 한도를 넘으면 그날은 더 이상 읽기/쓰기가 안 된다.
서버 비용을 아끼기 위해 선택한 구조이니, 반대로 이 할당량 안에서 최대한
효율적으로 동작하도록 만드는 책임도 같이 따라온다. 모임 상세 화면은
"같이 보는 사람들 사이에 실시간으로 동기화된다"는 게 핵심 가치라서
`onSnapshot` 기반 실시간 리스너를 쓰고 있는데, 이 실시간성과 읽기 효율을
동시에 만족시키는 게 이번 문제의 핵심이었다.

### 문제 상황

사용자가 실제로 앱을 쓸 때 가장 흔한 동선은 "모임 상세 화면에서 비용을
한 건씩 추가하는 것"이다. 화면 흐름으로 풀어보면:

1. `/meetings/:id` (모임 상세) — 멤버 목록, 지출 목록이 화면에 보임
2. "비용 추가하기" 버튼 클릭 → `/meetings/:id/expense`로 이동
3. 금액·결제자 입력 후 등록 → 뒤로가기로 다시 `/meetings/:id`로 복귀
4. 새로 추가된 지출이 목록에 반영된 걸 확인
5. 다음 비용을 또 추가하려고 2번부터 반복

겉보기엔 평범한 화면 전환인데, 이 한 번의 왕복마다 Firestore 읽기가
중복으로 발생하고 있었다. 같은 문제가 "모임 상세 → 방 정보 수정 →
뒤로가기", "홈 ↔ 내역 탭 전환"에서도 동일하게 나타났다. 즉 "화면을
잠깐 나갔다가 곧바로 돌아오는" 아주 흔한 패턴 자체가 매번 읽기 비용을
다시 지불하게 만들고 있었던 것이다.

### 원인 분석

이 문제는 두 가지 사실이 겹쳐서 발생했다.

**첫째, React Router의 라우트 구조.** `App.tsx`에 등록된 라우트들은
`/meetings/:id`, `/meetings/:id/edit`, `/meetings/:id/expense`,
`/meetings/:id/settle`처럼 모두 형제(sibling) 라우트로 평평하게
나열되어 있다. 공통 부모 레이아웃이나 `Outlet`으로 묶여있지 않기 때문에,
경로가 바뀌면 React Router는 이전 경로에 매칭됐던 컴포넌트를 완전히
unmount하고 새 경로에 매칭되는 컴포넌트를 처음부터 새로 mount한다.
즉 `MeetingDetail`에서 `ExpenseInput`으로 넘어가는 순간 `MeetingDetail`은
인스턴스 자체가 사라지고, 다시 돌아오면 똑같은 화면이지만 실제로는
"새로 태어난" `MeetingDetail` 컴포넌트다.

**둘째, Firestore 실시간 리스너의 과금 방식.** `useMeeting` 훅은
`onSnapshot`으로 모임 문서, `members` 서브컬렉션, `expenses`
서브컬렉션을 구독한다. Firestore의 실시간 리스너는 "리스너를 새로
맺는 시점"에 그 쿼리의 결과 집합 전체를 한 번 읽고, 그 이후부터는
실제로 추가/수정/삭제된 문서만큼만 읽기 비용이 발생하는 방식으로
과금된다. 다시 말해 리스너를 유지하고 있는 동안 데이터가 1건 바뀌면
1번만 읽히지만, 리스너를 끊었다가 다시 맺으면 "그 시점의 전체"를
다시 읽어야 해서 멤버가 4명이면 4번, 지출이 10건이면 10번을 한꺼번에
다시 읽는다.

이 둘을 합치면: 컴포넌트가 mount될 때마다 훅이 새 리스너를 맺고,
React Router가 화면을 오갈 때마다 컴포넌트를 새로 mount시키니, 결국
"화면 전환 = 멤버 전체 + 지출 전체를 처음부터 다시 읽기"가 되어버린
것이다. 사용자 입장에선 그냥 뒤로가기 버튼 한 번 누른 것뿐인데, 그
한 번이 데이터 규모에 비례하는 읽기 비용을 다시 발생시키고 있었다.

여기에 더해 개별 화면 단위의 중복도 있었다. `ExpenseInput.tsx`는
"정산이 이미 끝난 방인지" 확인하려고 모임 문서를 `getDoc`으로 한 번
더 읽었고, `MeetingEdit.tsx`도 방 이름·날짜·메모를 폼에 채우려고
모임 문서를 `getDoc`으로 또 읽었다. 둘 다 같은 모임 데이터를 상세
화면에서 이미 읽어온 직후인데도, 화면이 다르다는 이유만으로 매번
새로 읽고 있었다.

### 해결 방안 검토

네 가지 방법을 검토했다.

**1) React Router 레이아웃(Outlet)으로 상위에서 한 번만 구독하기.**
`/meetings/:id` 계열 라우트를 공통 레이아웃 라우트 하나로 묶고, 그
레이아웃 컴포넌트에서 `useMeeting`을 딱 한 번 호출한 뒤 `Outlet
context`로 자식 라우트들에게 데이터를 내려주는 방법이다. React가
원래 의도한 "상위에서 구독하고 하위는 받아서 쓴다"는 패턴에 가장
가깝다는 장점이 있다. 하지만 두 가지 문제가 있었다. 먼저 `App.tsx`의
라우트 트리를 통째로 재구성해야 하고, 이미 검증을 마친 4개 페이지
컴포넌트가 `useMeeting`을 직접 호출하던 방식에서 `useOutletContext`로
받아오는 방식으로 전부 바뀌어야 해서 변경 범위와 회귀 위험이 컸다.
또 레이아웃 자체도 사용자가 모임을 완전히 벗어나면(예: 홈 탭으로
이동) 같이 unmount되기 때문에, "화면을 잠깐 떠났다가 금방 돌아와도
구독을 유지한다"는 동작은 레이아웃 구조만으로는 자연스럽게 풀리지
않는다. 결국 캐시 유지 로직을 별도로 또 만들어야 했다.

**2) Zustand 전역 스토어에 모임 데이터를 캐싱하기.** 이미 `userStore`로
Zustand를 쓰고 있으니 자연스러운 선택지로 보였다. 하지만 막상 따져보면
Zustand는 "이 모임 ID는 지금 몇 명이 보고 있는지(참조 카운트)", "마지막
구독자가 떠난 뒤 일정 시간 안에 다시 들어오면 구독을 유지한다(유예
시간)" 같은 동적 키 기반 구독 생명주기를 기본으로 제공하지 않는다.
즉 Zustand를 쓰더라도 이 로직은 결국 내가 직접 구현해야 하는 건
동일했고, 오히려 전역 스토어의 갱신 알림 방식과 meetingId별 동적
구독을 맞추려다 보면 복잡도만 늘어나는 모양이 됐다. Zustand 자체가
이 문제에 본질적인 해법을 주지 않는다고 판단해 제외했다.

**3) 실시간 구독을 포기하고 필요할 때 한 번만 `getDoc`/`getDocs`로
읽기.** 화면에 들어갈 때 딱 한 번 읽고 끝내면 "다시 읽는다"는 문제
자체가 사라진다. 구현도 제일 단순하다. 하지만 이 방법은 띵돈의 핵심
기능, 즉 같은 모임을 보는 다른 사람이 비용을 추가하면 내 화면에도
실시간으로 반영되는 동작을 포기해야 한다. 정산 금액이 실시간으로
안 맞으면 앱의 신뢰도에 직접적인 문제가 생기므로 처음부터 후보에서
제외했다.

**4) (채택) 모듈 레벨 캐시 + `useSyncExternalStore` + 참조 카운트 +
유예 시간.** React 컴포넌트 트리 바깥에 `meetingId`(또는 `uid`)를
키로 하는 캐시를 모듈 레벨 `Map`으로 두고, 어느 컴포넌트든 같은 키를
구독하려고 하면 새 리스너를 맺지 않고 기존 구독을 그대로 재사용하는
방법이다. 구독자가 몇 명인지 참조 카운트로 추적하다가, 마지막
구독자가 사라져도 즉시 리스너를 끊지 않고 30초 동안 유예 시간을
둔다. 그 안에 같은 키로 새 구독 요청이 들어오면(화면을 빠르게 오간
경우) 예정된 해제를 취소해서 리스너를 계속 살려두고, 30초가 지날
때까지 아무도 다시 찾지 않으면 그때 실제로 리스너를 끊고 캐시에서
지운다.

### 채택 이유

4번을 선택한 핵심 이유는 "변경 범위를 가장 좁게 가져갈 수 있다"는
점이었다. `useMeeting(meetingId)`, `useMeetingMembers(meetingId)`,
`useMeetings(uid)`가 컴포넌트에게 돌려주는 값의 형태(시그니처)를
그대로 유지할 수 있었기 때문에, 이미 여러 차례 보안 점검과 버그
수정을 거쳐 검증된 4개 페이지 컴포넌트(`MeetingDetail`, `ExpenseInput`,
`MeetingEdit`, `Settle`)의 호출부 코드를 거의 건드리지 않고 적용할 수
있었다. 마감을 앞둔 상황에서 라우팅 구조나 `firestore.rules` 같은
회귀 위험이 큰 부분은 전혀 손대지 않고, 훅 내부 구현만 교체하는
가장 표적화된(targeted) 방법이라는 점이 가장 컸다. 더불어
`useSyncExternalStore`는 "React 트리 바깥에 있는 가변 데이터를 구독한다"는
바로 이 상황을 위해 React 18에서 공식으로 제공하는 API라서, 직접 만든
`Set`+`forceUpdate` 패턴보다 신뢰도 높은 정석적인 구현이 가능했다.

### 구현 상세

- `src/hooks/useMeeting.ts` — 모듈 레벨 `Map<meetingId, CacheEntry>`로
  구독을 관리한다. `CacheEntry`는 현재 상태(`meeting`, `members`,
  `expenses`, 로딩/에러 플래그), 구독 중인 컴포넌트들의 리렌더 콜백
  목록(`Set<() => void>`), 모임 문서·멤버·지출 3개의 `onSnapshot` 해제
  함수, 유예 타이머를 들고 있다. 같은 `meetingId`로 두 번째 구독
  요청이 들어오면 `Map`에서 기존 항목을 찾아 그대로 반환하고, 새
  리스너는 맺지 않는다.
- `src/hooks/useMeetings.ts` — 같은 패턴을 `uid` 키로 적용해 홈/내역
  탭이 "내 모임 목록" 구독을 공유하게 했다.
- `src/pages/ExpenseInput.tsx` — 정산 완료 여부를 확인하던 별도
  `getDoc`을 없애고, 이미 공유 캐시에 들어있는 `meeting.status`를
  그대로 사용하도록 바꿨다.
- `src/pages/MeetingEdit.tsx` — 모임 정보를 불러오던 별도 `getDoc`을
  없애고 공유 캐시의 `meeting`/`members`를 사용한다. 다만 이 화면은
  이름·날짜·메모를 사용자가 직접 수정하는 폼이라서, 실시간 데이터가
  계속 흘러들어오는 것을 그대로 폼에 반영하면 입력 중인 값이 갑자기
  덮어써질 위험이 있다. 그래서 `ref`로 "최초 1회만 폼에 채워넣고,
  그 이후의 실시간 갱신은 폼에 반영하지 않는다"는 가드를 추가해서
  기존 동작(처음 불러올 때 한 번 채우고 끝)을 그대로 유지했다.

### 검증 방법

코드 리뷰만으로는 "정말로 중복 구독이 사라졌는지"를 확신할 수 없어서,
`firebase/firestore`의 `onSnapshot`을 모킹해 호출 횟수를 직접 세는
테스트를 작성했다(`src/hooks/useMeeting.test.tsx`,
`src/hooks/useMeetings.test.tsx`). 확인한 항목은 세 가지다.

1. 같은 `meetingId`(또는 `uid`)를 빠르게 mount → unmount → remount해도
   `onSnapshot`이 추가로 호출되지 않고 정확히 처음 한 번만 호출되는지
2. 유예 시간(30초)이 실제로 지난 뒤에 다시 mount하면, 그때는 새
   `onSnapshot` 구독이 정상적으로 다시 일어나는지(영구 누수가 아니라는
   것의 확인)
3. 서로 다른 `meetingId`를 구독하는 두 컴포넌트가 캐시를 공유하지
   않고 각자 독립적으로 동작하는지

세 가지 모두 테스트로 통과를 확인했고, 이와 별개로 타입체크(`tsc`),
ESLint, 기존 단위테스트(`format.test.ts`, `settle.test.ts`), 프로덕션
빌드(`vite build` + `.ait` 빌드)까지 전부 정상적으로 통과하는 것을
확인했다.

### 결과 (수치)

아래 수치는 Firebase 콘솔의 실시간 사용량 대시보드에서 직접 측정한
값이 아니라, Firestore가 공식적으로 명시하는 읽기 과금 규칙—"리스너를
새로 맺는 시점에는 그 쿼리의 결과 집합 전체를 읽고, 그 이후에는 실제로
바뀐 문서 수만큼만 읽는다"—을 수정 전/후 코드의 실제 동작에 그대로
대입해서 계산한 값이다. 즉 "이 코드가 정확히 이렇게 동작한다면 발생할
읽기 횟수"를 식으로 환산한 결과이며, 실제 운영 트래픽을 측정한 것은
아니라는 점을 밝혀둔다.

**시나리오 A — 멤버 4명인 모임에서, 상세 화면과 비용 추가 화면을
오가며 비용을 5건 연달아 추가하는 경우**

수정 전에는 다음과 같이 읽기가 누적된다.

- 최초로 상세 화면에 들어갈 때: 모임 문서 1 + 멤버 4명 + 지출 0건 = 5회
- 비용 추가 화면에 들어갈 때마다: 정산여부 확인용 `getDoc` 1 + 멤버
  구독 4명 = 5회. 이걸 5번 반복하므로 5 × 5 = 25회
- 비용을 실제로 등록할 때마다, 그 시점에 살아있는 지출 리스너가 새
  문서 1건을 감지: 5번이니 5회 (이 부분은 수정 전후 동일)
- 비용 등록 후 상세 화면으로 돌아올 때마다: 그 시점의 멤버 4명 +
  지출 전체(1건, 2건, 3건, 4건, 5건)를 처음부터 다시 읽음. 모임 문서
  1 + 멤버 4 + 지출 N을 5번 더하면 (1+4+1)+(1+4+2)+(1+4+3)+(1+4+4)+(1+4+5)
  = 6+7+8+9+10 = 40회

합계: 5 + 25 + 5 + 40 = **75회**

수정 후에는 비용 추가 화면도 상세 화면도 이미 만들어진 캐시를 그대로
재사용하므로, 화면을 오가는 데서 발생하는 읽기가 0이 된다. 실제로
데이터가 바뀐 시점(비용이 새로 등록된 시점)에만 그 변경분만큼만 읽힌다.

- 최초 상세 화면 진입: 5회 (동일)
- 비용 추가 화면 진입 ×5: 0회 (캐시 재사용)
- 비용 등록 시 변경분 반영 ×5: 5회 (동일)
- 상세 화면 재진입 ×5: 0회 (캐시 재사용)

합계: 5 + 0 + 5 + 0 = **15회**

75회에서 15회로, **80% 감소**한다.

**시나리오 B — 모임을 6개 가진 사용자가 홈 탭과 내역 탭을 5번 오가는 경우**

수정 전: 최초 진입 6회 + 이후 탭 전환 4번마다 매번 모임 6개를 다시
읽음(6 × 4 = 24회) = **30회**
수정 후: 최초 진입 6회 + 이후 탭 전환 4번은 캐시 재사용으로 0회 =
**6회**

30회에서 6회로, 역시 **80% 감소**한다.

두 시나리오의 공통된 특징은, 수정 전 비용이 "화면을 오간 횟수 ×
데이터 규모(멤버 수, 모임 수)"에 비례해서 계속 불어나는 구조였던
반면, 수정 후 비용은 화면 전환 횟수와 거의 무관하게 일정하다는
점이다. 즉 멤버가 더 많은 모임이거나, 사용자가 화면을 더 자주
오가는 습관이 있을수록 절감 효과는 80%보다 더 커진다. 반대로 멤버가
1명뿐이고 화면을 딱 한 번만 본다면 절감 효과는 거의 없다(애초에
중복이 발생할 기회가 없으므로). 이번 두 시나리오는 "비용을 여러 건
나눠서 추가하는" 가장 흔한 실사용 패턴을 기준으로 잡은 것이다.

### 한계 및 남은 고려사항

- 위 수치는 실제 대시보드 계측이 아닌 과금 규칙 기반 계산값이다.
  실제 운영 환경에서 Firebase 콘솔의 사용량 그래프로 재확인하면 더
  신뢰할 수 있는 수치가 될 것이다.
- 유예 시간(30초)은 "화면을 빠르게 오가는 경우는 살리고, 진짜로
  떠난 경우는 정리한다"는 목적에 맞춰 임의로 정한 값이다. 실제 사용
  패턴을 더 관찰하면 더 적절한 값으로 조정할 수 있다.
- `firestore.rules` 안의 `get()`/`exists()` 호출도 처음엔 중복 읽기로
  의심했지만, Firestore는 같은 요청 안에서 같은 문서를 다시 조회하면
  자동으로 캐싱해 한 번만 과금한다고 공식 문서에 명시되어 있어 별도로
  손대지 않았다. 보안 규칙은 이미 여러 차례 에뮬레이터·운영 환경
  검증을 거친 부분이라, 불확실한 이득을 위해 다시 흔들 필요는 없다고
  판단했다.
